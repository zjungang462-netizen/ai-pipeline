## 审查重点
- **正确性**：逻辑缺陷、边界条件、竞态、状态机漏洞、续跑/恢复一致性。
- **安全性**：命令注入、路径遍历、密钥泄漏、越界写入、不受信输入处理。
- **健壮性**：错误处理、异常分类、超时、资源清理、失败是否静默。
- **可维护性**：模块边界、重复逻辑、死代码、文档与实现是否一致。
- **测试覆盖**：关键路径与异常路径是否有测试，是否存在"测试掩盖缺陷"。

## 输出要求
- 按严重度分级列出问题（阻断 / 重要 / 次要），每条给出：文件、位置、问题、期望修复。
- 只报**真实可验证**的问题，指明依据；不要臆测未给出的代码。
- 若某方面确实做得好，简要肯定，不要为凑数编造问题。
- 输出审查报告（Markdown）。

## 结构化结论（必须，供引擎解析）
报告末尾附一个 JSON 代码块：

```json
{"verdict": "pass", "issues": []}
```

- `verdict`：`"pass"`（无阻断问题）或 `"fail"`（存在阻断问题）。
- `issues`：逐条列出必须修复的问题（字符串）。
