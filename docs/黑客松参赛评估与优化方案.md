## 参赛判断

**可以演示，建议修完参赛入口和交付门禁再提交。** 面向一个需要审核 AI 代码的开发者，最有说服力的场景是亲眼看到一次错误实现被真实测试拦下，看到第二次修改的 diff，再决定是否接收。仓库已经能执行这个过程。当前给评委的入口只展示生成文件、验证文件存在、人工放行，最能说明项目价值的部分藏在命令行基准里。

英文首页面向 **Kiroween 2026 / Frankenstein**。Devpost 的活动目录将 Kiroween 2026 列为 Kiro 主办，提交期为 **2026 年 10 月 30 日至 12 月 4 日**。本次可访问的目录只列日期。此前写为北京时间 12 月 5 日 06:00 的截止时刻需要在报名后台核实，排期请预留一天。报名资格、既有代码披露和评分权重也以本届规则为准。仓库的首个可见提交为 2026 年 11 月 15 日的 `758a542`。[Devpost 赛事目录](https://devpost.com/api/hackathons?search=kiroween) · [赛事规则](https://kiroween.devpost.com/rules)

建议准备一个可下载的构建、一段三分钟以内的英文演示和一页测试步骤。用一次真实的 Kiro 开发记录展示 spec 如何约束实现、hook 怎样发现问题。评委可以用视频理解案例，再从干净设备启动工作台复核证据。

### 当前提交的回归结果

| 实际运行 | 通过 | 断言失败 | 测试错误 | 跳过 | 总耗时 | 出口 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Windows quick | 251 / 259 | 0 | 8 | 0 | 150.281 秒 | 1，超过 120 秒硬门槛 |
| Windows full | 797 / 812 | 1 | 14 | 0 | 1,050.204 秒 | 1，超过 480 秒报告目标 |

两套运行各用一个测试工作进程，部分时段与其他检查并行。原始收据均记录产品文件指纹一致。**14 个全量错误都发生在临时仓库 `git init` 返回 128 时**，涉及竞技场、Git 辅助函数、提交门禁、清理和打包。另一个失败来自双进程完整性用例，首进程未在 15 秒内产生进入标记。

定位时捕获到 `missing config value GIT_CONFIG_VALUE_0`。用本机 Python 做最小对照，同一进程先运行 `git init` 返回 0，经过一次 `mock.patch.dict(os.environ, …)` 的设置和还原，再执行同一命令即返回 128。Python 映射里的 Git 配置值仍显示为空字符串。保留该配置，诊断时让 Git 子进程显式继承 Python 的环境映射，对原先 15 个失败项定向复跑，得到 **15/15 通过**。双进程用例在两次独立小组复跑中也均通过，其超时原因仍待重现。这给出了修复测试环境和收集诊断的方向，正式候选提交还需按原命令完整通过。

GitHub 同一 SHA 的 Windows Python 3.11 和 3.13 作业均在 `Quick offline acceptance` 失败。远端失败用例需要从该次产物读取，不能据本机现象推定远端根因。建议先比对两份 CI 收据，再分别修复环境继承、偶发超时或运行时长。验收以同一 SHA 两个远端作业全绿、本地全量 0 失败/错误为准。[该提交的 GitHub Actions 记录](https://github.com/zjungang462-netizen/ai-pipeline/actions/runs/45740253448)

CLI 退出码、浏览器运行终态、基准尝试次数与失败用例均可逐条复核。[脱敏测试摘要及失败用例清单](hackathon-audit-2026-11-26.json)

## 赛前排期和演示脚本

**只有一天时**，先核对赛事和修复模板选择，再把 `test_repair` 变成台前演练，最后录制一次带证据的完整过程。剩余时间集中排查会影响主路径的验收失败。多出一天时，补真实样例、英文操作路径、外部盲测和候选提交的全量验收。多工具兼容表、竞技场和主题都可作为评委追问时的补充。

| 建议用时 | 在台上做什么 | 评委能验证什么 |
| --- | --- | --- |
| 0:00–0:25 | 用一个输入讲需求，`normalize(" A  B ")` 应输出 `a-b`，启动明确标为离线的演练 | 任务足够小，非作者也能预判正确结果 |
| 0:25–1:10 | 展开第一次测试失败，展示退出码、失败断言和退回编码事件 | 代码文件存在，交付仍被工程规则拦下 |
| 1:10–2:00 | 点击第二次 diff、同一组测试的通过记录与独立审查结论 | 修的是实现，保护测试指纹保持一致 |
| 2:00–2:40 | 展示待审批，批准后核对终态，再打开脱敏真实运行收据 | 谁做了决定、何时完成、哪些阶段用过真实模型，都有出处 |
| 网络或模型不可用 | 继续使用本地离线任务，切换到预先保存的真实运行证据并显示录制日期 | 现场执行与历史回放有明确标签 |

## 开发者复验

在新克隆的 `agent-orchestrator` 目录执行下列 PowerShell 命令。运行目录按次生成，便于对照同一提交的不同结果。`--quick` 有 120 秒硬门槛，`full` 的 480 秒是报告目标。串行单独测时再讨论性能。

```powershell
$proof = Join-Path ([IO.Path]::GetTempPath()) ('pipeline-audit-' + [guid]::NewGuid().ToString('N'))
$env:PYTHONUTF8 = '1'
$demoId = 'judge-' + [guid]::NewGuid().ToString('N').Substring(0,8)
python -m orchestrator.cli doctor kiroween-demo.example.toml
python -m orchestrator.cli run kiroween-demo.example.toml --task 'Build demo module' --run-id $demoId
# 这里预期退出 11，等待人工验收
python -m orchestrator.cli status kiroween-demo.example.toml --run-id $demoId
python -m orchestrator.cli approve kiroween-demo.example.toml --run-id $demoId --stage acceptance
python scripts/benchmark.py --output "$proof/bench"
python scripts/verify_delivery.py --quick --redact-logs --output "$proof/quick"
python scripts/verify_delivery.py --suite full --redact-logs --output "$proof/full"
```

网页验收可单独启动 `python -m orchestrator.cli dashboard --config kiroween-demo.example.toml --port 0`，打开命令输出的本机会话链接。参赛材料可引用运行提交、阶段状态、退出码和哈希。包含会话链接的控制台、数据库与原始日志留在本地。
