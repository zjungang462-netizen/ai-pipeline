## 1. 结论

可以参赛，但不建议按现状提交。引擎、证据链和审批闭环是真实可用的，问题几乎全部集中在“评委第一次上手”这条路径上。

按“对评审的影响除以工时”排序，建议先做 P0-1、P0-3、P0-6、P0-7 的 hook 修复，合计约半天到一天，先把仓库恢复到“本机干净克隆全绿、推送后 CI 变绿”。再做 P0-2 和 P0-5，这是演示本身的价值。P0-4 工时最长，但对国际评委能否独立完成试用影响最大。

## 3. 问题与改法

### P0：提交前必须处理

#### P0-1 演示第二次运行，编码阶段必定先失败一次

证据：同一工作区连续运行时，编码阶段第 1 次尝试交替失败。工作区提交里 `CALL` 的值依次是 1、2、1、2、1，中间夹着失败的那次。界面运行 3 次、命令行 2 次均符合这个规律。失败类型是 `archive`，我在克隆里加了一行插桩，取到原因是“代码未发生变化，无法视为一次修复”。整体仍以退出码 11 到达审批，所以容易漏掉。

根因：

- `agent-orchestrator/orchestrator/adapters/fake.py:59-61` 写入的文件带一行 `CALL = self.calls`。每次新运行都是新进程，首次调用恒为 1。
- 上一轮如果一次通过，文件内容就与这次完全相同。`agent-orchestrator/orchestrator/archive.py:97-99` 判定零变更并抛出 `StageArchiveError`。
- `agent-orchestrator/orchestrator/execution.py:403-415` 把这次尝试记为失败并重试，第二次序号变成 2 才通过。

改法：让假执行器的产物每次运行都不同，例如把 `ctx.run_id` 写进文件。一行改动。

验收：同一工作区连续 `run` 加 `approve` 五轮，每轮编码阶段只有一条 `attempt_start` 和一条 `attempt_done`。

工时：1 小时，含回归。

#### P0-2 演示内容是空壳，4.6 秒结束

证据：

- 空闲机器（CPU 约 36%）上，从点击“启动演示流程”到待审批共 4.55 秒：0.13 秒创建任务，1.38 秒第一阶段开始。机器满载时约 16 秒。命令行整条流水线 2.39 秒，0 token。
- 产物是两个 3 行的报告（`fake.py:52`）和一个 4 行的 `coding_output.py`（`fake.py:59-61`）。
- `agent-orchestrator/kiroween-demo.example.toml:72` 的测试只断言文件存在。另一份方案实测 0 字节文件也能通过，我认同这个结论。`:84` 的“人工验收”阶段只打印一句话。

改法：同意另一份方案的 `test_repair` 思路，即首个实现故意不过真实测试，被打回后第二次修复，再经独立审查和审批。我补充三点：

1. 产物要“像真的”：有函数、有测试、有可看的 diff。
2. 测试断言行为。空文件、原样返回、大小写错误都必须非零退出。
3. 给假执行器加一个可配置的节奏，每个阶段用 0.5 到 1 秒推进度事件，否则评委跟不上。

验收：新克隆运行 3 次都在 60 秒内到达审批；界面上能看到失败断言、第二次 diff 和 `review_verdict.json`。

工时：4 到 6 小时。

#### P0-3 非中文 Windows 上命令行崩溃

证据：设 `PYTHONIOENCODING=cp1252` 并把输出重定向后，`doctor` 和 `run` 都退出 1，报 `UnicodeEncodeError: 'charmap' codec can't encode characters`。`--version` 正常。触发条件是 stdout 被重定向或走管道，例如 Git Bash、Cygwin、`> log.txt`、`| tee`，或被别的工具调用。直接在 cmd、PowerShell、IDE 终端里运行不受影响。

根因：`agent-orchestrator/orchestrator/cli.py:398` 的 `main()` 没有处理输出流，而所有文案都是中文。CI 里设了 `PYTHONUTF8=1`，所以一直没暴露。

改法：在 `main()` 开头加几行。非 UTF-8 且非终端的流重配为 UTF-8，终端流保留原编码，并统一 `errors='backslashreplace'`，保证任何情况下不崩溃。代价是中文 Windows 上重定向输出的字节从 GBK 变成 UTF-8，旧的 GBK 工具读取会乱码；如果介意，只加 `errors='backslashreplace'` 也能止住崩溃。根治办法是 P0-4，英文输出全是 ASCII。

验收：`PYTHONIOENCODING=cp1252 python -m orchestrator.cli doctor kiroween-demo.example.toml > out.txt` 退出 0；补一条子进程回归用例。

工时：1 到 2 小时。

#### P0-4 产品只有中文

证据：

- `index.html` 为 `lang="zh-CN"`，4 个静态文件共 274 行含中文（51、116、94、13）。
- `app.js:27-28` 等位置把 `zh-CN` 写死，没有任何多语言层。

- 英文 README 只有 66 行，没有一张图。

- 路线 A，全量国际化。前端文案抽表，后端消息建字典。约 2 到 3 天，回归面大。
- 路线 B，只做评委路径的英文化。增加 `PIPELINE_LANG=en` 或 `--lang` 开关，覆盖命令行通用提示，以及首页、新建任务、阶段进度、审批、证据面板、动态流标签。约 1 到 1.5 天。

建议走路线 B，并在主题切换旁加一个中英文开关。时间有富余再扩展成路线 A。

验收：英文模式下从首页到审批完成，可见文本里 CJK 字符为 0；现有界面测试全部通过。

工时：1 到 1.5 天。

#### P0-5 两个主打功能在零密钥演示里不可用，竞技场还会调用真实 CLI

证据：

- 圆桌会诊按钮对演示项目不显示。`agent-orchestrator/orchestrator/collaboration/service.py:178-180` 要求配置里含有 `openai_compat` 或 `cli_agy` 适配器，`app.js:171` 据此隐藏按钮。命令面板（`app.js:572`）只要选中了任务就会列出“发起多模型圆桌会诊”，它做的事是对那个隐藏按钮模拟一次点击。
- 竞技场只提供真实 CLI 作为候选。我在临时克隆里点了“开始双模型并行比拼”，它确实启动了本机 `agy` 两次，各约 50 秒后停在登录提示，最后报“全部候选执行失败”，token 为 0。如果评委机器上的 CLI 已登录，就会产生真实调用和费用。

改法：

- 必做：项目处于模拟模式时禁用竞技场并说明原因，命令面板同步过滤。`agent-orchestrator/orchestrator/collaboration/execution_scope.py:10-19` 已经算出了 `mode == 'simulation'`，直接复用。约 0.5 小时。
- 加分：给竞技场和圆桌各加一个离线回放模式。竞技场用两个脚本化候选，产出不同的补丁，diff 比较和 `--ff-only` 合入逻辑照常执行；圆桌用带“离线回放”标识的预置四角色记录。约 3 到 4 小时。

验收：在演示项目里点竞技场，不会启动任何真实 CLI；圆桌有可见入口，并明确标注为回放。

- 空闲机器上单独重跑仍失败，约 2 秒即失败。在你的工作区里同样失败。
- 你的 `agent-orchestrator/.test-failures/` 里，11-25 18:22 到 18:30 已经有同一组用例的失败证据。

证据，远端：

- `main` 上由推送触发的 Offline Checks 已经连续失败 18 次，从 `922acc0`（北京时间 11-22 00:28）到当前提交。最后一次通过是 `121791c`。评委打开仓库的提交列表，看到的是一排红叉。
- 当前提交 `0b3f30d` 的两个作业 `quick (3.11)` 和 `quick (3.13)` 都在 “Quick offline acceptance” 这一步失败。
- 第一次失败的提交 `922acc0` 只改了三个前端静态文件：`app.js`、`index.html`、`style.css`。
- 远端具体败在哪个用例，我不知道。作业日志和产物 `offline-<Python 版本>-<提交号>` 都要登录才能下载。

本机这 11 项的根因，已用最小实验坐实：不是产品回归，是测试垫片的编码问题。

- `agent-orchestrator/tests/test_cli_reliability.py:47` 和 `agent-orchestrator/tests/test_process_start.py:55` 把 `.cmd` 垫片按 UTF-8 写入，内容里带有 `sys.executable`。
- 本机 Python 装在 `C:\Users\张军刚\...` 下。cmd.exe 按代码页 936 读批处理文件，中文路径被读错，报“系统找不到指定的路径”。
- 对照实验：同一份垫片按 UTF-8 写入，退出 1；按系统 ANSI 编码写入，退出 0。

你在 `WORK_STATUS.md:102` 和 `:105` 记录的全量通过证据保存在另一个目录 `D:/work/ai-pipeline-release-056-cb48f023/` 下，`:145` 用的是嵌入式 CPython 的解释器副本。这些运行为什么没有撞上垫片问题，我没有核实；推断是当时用的解释器路径不含中文。

这 11 项 CI 没拦住的原因：`.github/workflows/ci.yml:50` 只跑 quick，而 `agent-orchestrator/scripts/verify_delivery.py:27-37` 的 `QUICK_TESTS` 不包含这两个模块。

远端那 18 次失败是另一回事，我在本机没有复现。按 CI 的条件逐项对齐后重跑 quick，全部通过：便携版 Node 22.23.5、单工作进程、`TEMP` 指到仓库之外、全新克隆且文本文件统一为 CRLF（259 项 0 失败，67 秒）、全新克隆且全部为 LF（259 项 0 失败，107 秒）。剩下的差异只能在 CI 的机器环境里，我没有条件逐项验证。

和另一份方案的数字对不上，原因在这里：

- 另一份方案在同一提交上得到 quick 251/259（8 个错误）和全量 797/812（1 个失败加 14 个错误），和我的 11 项不是同一组。
- 它多出的 14 个错误是 `git init` 返回 128。我用不涉及产品代码的探针复现了机制：进程环境里 `GIT_CONFIG_VALUE_0` 是空字符串时，第一次 `git init` 返回 0；进程里只要经历过一次 `mock.patch.dict(os.environ, …)` 的还原，`os.environ` 里它仍显示为空字符串，子进程却已经收不到它，`git init` 转而报 `missing config value GIT_CONFIG_VALUE_0`。
- 我的进程环境里没有任何 `GIT_CONFIG_*` 变量，所以没有遇到。这组错误取决于运行测试的那个会话的宿主环境，评委的终端里通常没有这些变量。那个会话的环境里具体有什么，我没有看到，这一句是推断。
- 它剩下的 1 个失败是双进程用例的 15 秒超时，和机器负载有关，我这边没有出现。

改法：

1. 垫片里使用 8.3 短路径，或者按系统 ANSI 编码写入。短路径更稳，西欧 Windows 的 ANSI 代码页和 OEM 代码页并不相同。
2. CI 增加一个跑全量的作业，至少 Windows 一份，由 PR 触发。
3. 登录 GitHub 打开这次运行，下载产物 `offline-3.11-0b3f30d…`，读里面的 `ci-evidence/verification.json` 和 `quick-regression.log`，按实际失败的用例修。产物只保留 14 天，要在 12-10 之前取。
4. 测试进程启动时清掉取值为空的 `GIT_CONFIG_*` 变量，或者让 Git 子进程使用显式的环境映射。约 0.5 小时，只影响带这类环境变量的会话。

验收：用本机默认 `python`（中文路径）跑全量，0 失败；候选提交推送后两个 CI 作业都通过。

工时：2 到 3 小时。第 3 项取决于远端日志里是什么。

说明：ASCII 用户名的评委不会遇到这个问题。但一个以“证据优先”为卖点的项目，自己的全量验收在这类机器上不过，是说不过去的。

#### P0-7 Kiro 使用证据只有一个，而且 hook 跑不通
